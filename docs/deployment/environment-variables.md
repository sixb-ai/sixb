# Environment variables

Keep your project's values in [Doppler](https://www.doppler.com) or [Azure Key Vault](#azure-key-vault) instead of sending `.env` files around. The repository lists the names, `sixb env pull` writes your `.env`, and your app reads `process.env` as it always has.

## List what the project needs

`sixb.env.ts` holds names only, so commit it:

```ts
import { defineEnv } from "@sixb/core/env"
import { doppler } from "@sixb/env-doppler"

export default defineEnv({
  source: doppler({ project: "client-a" }),
  vars: {
    DATABASE_URL: "required",
    LINKEDIN_CLIENT_SECRET: "prod",
    SENTRY_DSN: "optional",
  },
})
```

| Rule | The variable must have a value |
| --- | --- |
| `required` | Everywhere |
| `prod` | In `prod`, and when `NODE_ENV` is `production` |
| `optional` | Never. The name is only recorded |

`sixb dev` and `sixb check` stop before starting when a variable has no value, and an empty value counts as none. In a terminal, `sixb dev` offers to pull:

```text
Missing RESEND_API_KEY, which sixb.env.ts requires.
Pull from dev now? (Y/n)
```

`source` is optional. Without it you keep your own `.env`, and still get these checks. A project without `sixb.env.ts` runs without them.

## Move a project over

Create the project in Doppler, install the package and the [Doppler CLI](https://docs.doppler.com/docs/install-cli), then upload your current files:

```bash
bun add @sixb/env-doppler
bun sixb env init client-a --dev .env --prod .env.prod
```

This uploads the values and writes `sixb.env.ts` with a first guess at each rule. Check the rules, commit the file, and delete `.env.prod`. It stops without changing anything if Doppler already has a different value for a name.

## Work with the values

| Task | How |
| --- | --- |
| Start on a project | `bun sixb env pull`. The first time, it signs you in to Doppler |
| Get a teammate's change | `bun sixb env pull` |
| Add or change a value | `bun sixb env set <NAME> --env <dev\|prod>`, or Doppler's dashboard |
| See what's set | `bun sixb env status`, which never shows values |
| Add or remove a teammate | Doppler's dashboard. When someone leaves, rotate what they could read |

`sixb env set` asks for the value with a hidden prompt, or reads it from standard input, so it never lands in your shell's history.

`sixb env status` reads names only, so it shows a value that was blanked in Doppler as set. A pull and a deploy still stop on it.

Doppler accepts uppercase names only, and reads `${NAME}` in a value as a reference to another variable, which it resolves before `.env` is written. It refuses a reference it can't resolve, along with any other name or value it won't take, and says why.

### Your `.env`

`sixb env pull` replaces `.env`, so put your own overrides in `.env.local`, which takes priority. If you wrote the current `.env` by hand and it has values Doppler doesn't, the pull stops and names them rather than losing them. Pass `--force` to replace it anyway.

A pull stops, leaving `.env` as it was, when a variable `sixb.env.ts` requires isn't in Doppler. It also stops, naming the variable, for a value a `.env` file can't hold: one with a carriage return, one ending in a backslash, or one using all of `'`, `"` and `` ` ``.

### Production values

`sixb env pull` writes `dev`, and refuses `prod` on your computer so production values stay on your servers. To read one, use Doppler's dashboard. Deploying doesn't need your computer to hold them: [the server pulls for itself](#deploy).

## Deploy

With `source` set, each [deploy to a server](servers.md) writes that release's `.env` from `prod`, so there's nothing to edit on the server. The server reads with a read-only token for this project's `prd` config and nothing else, at `~/<name>/env-token`, mode 600. Whatever provisions the server puts it there, such as Terraform's Doppler provider, or you, once:

```bash
doppler configs tokens create sixb-shop --project shop --config prd --access read --plain |
  ssh deploy@203.0.113.10 'mkdir -p ~/shop && umask 077 && cat > ~/shop/env-token'
```

To replace it, revoke it in Doppler and write the new one over it.

A deploy pulls before it builds, while the live release keeps serving, so a pull that fails leaves it alone:

| What happens | The deploy |
| --- | --- |
| `sixb.env.ts` requires a variable `prod` doesn't have | Stops and names it |
| Doppler refuses the token | Stops |
| Doppler can't be reached | Continues on the current `.env` with a warning, if it was generated by a pull and has every required variable. Otherwise stops |
| The server's `.env` was written by hand, with values `prod` doesn't match | Stops and names them. Move what you want to keep to Doppler, then delete the file |

Your app reads only `.env`, so a running service or a restart never depends on Doppler. Changing a value in Doppler reaches the server at the next deploy. Each release keeps the `.env` it was deployed with; rolling back with `--ref` pulls the current values, so a key you revoked doesn't come back.

Anyone who can sign in to the server as the deploy account can read `.env` and the token, and so can a [CI job](github-actions.md) that deploys. Limit that access to people you'd trust with production.

## Tests in CI

Give a test job that needs values a read-only token for `dev`, created in Doppler:

```yaml
- env:
    DOPPLER_TOKEN: ${{ secrets.DOPPLER_DEV_TOKEN }}
  run: bun sixb env pull
```

## Azure Key Vault

To keep the values in Azure instead, use a vault for each environment:

```ts
import { defineEnv } from "@sixb/core/env"
import { azureKeyVault } from "@sixb/env-azure-key-vault"

export default defineEnv({
  source: azureKeyVault({ vaults: { dev: "client-a-dev", prod: "client-a-prod" } }),
  vars: { DATABASE_URL: "required" },
})
```

Install the package and the [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli), and sign in with `az login`. If the vaults are in a tenant other than your default, add `tenant: "<tenant ID or domain>"`.

To move a project over, write `sixb.env.ts` as above with `vars: {}`, then upload your current files without naming a project:

```bash
bun add @sixb/env-azure-key-vault
bun sixb env init --dev .env --prod .env.prod
```

It uploads to the vaults `sixb.env.ts` names and fills in `vars` with a first guess at each rule, stopping without changing anything if a vault already has a different value for a name. If `vars` isn't empty, it leaves the file alone and prints the rules to add.

Everything else works the same way, with these differences:

| | With Key Vault |
| --- | --- |
| Access | Pulling needs the Key Vault Secrets User role on the dev vault; `sixb env set` needs Key Vault Secrets Officer. Add and remove teammates in the Azure portal |
| Names | Key Vault allows hyphens, not underscores, so `DATABASE_URL` is stored as `DATABASE-URL`, and a secret you name `STRIPE-KEY` in the portal arrives as `STRIPE_KEY`. Names ignore case |
| Disabled secrets | Skipped, as if they weren't there |
| Deleted secrets | Setting a name you deleted recovers the secret with the new value |
| Tests in CI | Sign in with [`azure/login`](https://github.com/Azure/login) before `bun sixb env pull` |

The server reads with a service principal that can read the prod vault and nothing else: the Key Vault Secrets User role on a vault using Azure RBAC, or a `get` and `list` access policy on one using access policies. Its credential goes on the server at `~/<name>/env-token`, mode 600, as JSON:

```json
{ "tenant": "<tenant ID>", "clientId": "<app ID>", "clientSecret": "<secret>" }
```

`az ad sp create-for-rbac --name sixb-shop --role "Key Vault Secrets User" --scopes <vault ID>` prints those three values. When a deploy stops with `AADSTS7000222`, the secret expired: write a new one over the file.

### Read with the server's managed identity

On an Azure VM, the server can read the vault with the VM's [managed identity](https://learn.microsoft.com/entra/identity/managed-identities-azure-resources/overview) instead. Nothing is created, and nothing expires:

```ts
source: azureKeyVault({
  vaults: { dev: "client-a-dev", prod: "client-a-prod" },
  server: { identity: "managed" },
}),
```

The server then needs no credential and no `~/<name>/env-token`. The VM needs an identity, and someone who can grant access to the prod vault lets it read secrets there, once. The first deploy prints the exact command, with the identity's object ID. Run it signed in to the vault's subscription (`az account set --subscription <id>`):

```bash
az role assignment create --role "Key Vault Secrets User" --assignee-object-id <object ID> --assignee-principal-type ServicePrincipal --scope "$(az keyvault show --name client-a-prod --query id --output tsv)"
```

On a vault using access policies, it's `az keyvault set-policy` with `get` and `list` on secrets instead. A new role assignment takes a minute or two to apply. If the VM has no identity, the deploy prints the `az vm identity assign` command that turns one on.

To read with a user-assigned identity, add its client ID: `server: { identity: "managed", clientId: "<client ID>" }`.

To move a server that reads with a service principal, let its identity read the vault, then add `server` and deploy: from then on it reads with the identity. Then delete the old app registration.
